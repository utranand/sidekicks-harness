## Install — start here

**This one line is the install.** It is the supported path on every platform; everything else in
this README describes a workspace the installer has already created.

```sh
curl -fsSL https://raw.githubusercontent.com/utranand/sidekicks-harness/main/install.sh | sh -s -- --ref v1.2.3
```

> **The `--ref` is not optional decoration.** This README describes **v1.2.3**. Without it the
> installer mounts whatever `main` currently serves, which is a different version
> whenever a release has been tagged but not pushed — and every command, path and count documented
> below would then describe something you did not install. Verify what you got with
> `node bin/sidekicks core status`.

> **Cloning this repository is not an install.** A clone *is* the framework core — the very thing
> the installer mounts at `.sidekicks-core/` — so it has no `projects/`, no workspace `.sidekicks/`,
> and no `sidekicks/` directory inside it. Run the installer instead; it creates
> `sidekicks/` (rename with `--dir`) and mounts this repository at `.sidekicks-core/`, which is
> dot-prefixed and therefore invisible to a plain `ls`.

With options (the installer reads them from `sh -s --`):

```sh
curl -fsSL https://raw.githubusercontent.com/utranand/sidekicks-harness/main/install.sh | sh -s -- --dir my-workspace --ref v1.2.3
```

Windows (PowerShell):

```powershell
irm https://raw.githubusercontent.com/utranand/sidekicks-harness/main/install.ps1 -OutFile install.ps1
./install.ps1 -Dir my-workspace -Ref v1.2.3
```

| Option | Meaning |
|---|---|
| `--dir <path>` | workspace directory (default `sidekicks`) |
| `--ref <ref>` | framework tag or branch to pin (default `main`; this release is `v1.2.3`) |
| `--remote <url>` | framework remote to mount (default this repository) |
| `--no-init` | mount only; run `core init` yourself |

Requirements: **git** and **Node.js ≥ 20**. Nothing else — the framework has zero npm runtime
dependencies, so there is no install step, no build and no bundler.

## What you get

```
my-workspace/
├── .sidekicks-core/       ← this repository, mounted read-only and pinned to a ref
├── .sidekicks/            ← YOURS: config, memory, agents
├── .agents/skills/        ← YOURS: skills you write (a real directory beats a core skill)
├── projects/              ← YOURS: the work
├── bin/sidekicks          ← forwards into the mount
├── AGENTS.md              ← YOURS, importing the framework's rules from the mount
└── CLAUDE.md, GEMINI.md   ← symlinks to AGENTS.md, so every CLI reads one surface (Rule 6)
```

`AGENTS.md` is the instruction surface — the CLI-neutral standard filename. `core init` puts a
delimited managed block at the top of it importing the framework's own rules from
`.sidekicks-core/AGENTS.framework.md`. Edit `AGENTS.md`, never the mirrors.

The split is the point: **the core updates, your workspace persists**. `core update` rewrites only
framework-owned files (the CLI shim, the per-CLI hook wiring) and refreshes managed blocks inside
`.gitignore` and `AGENTS.md`. It never touches your config, your memory, your projects, or a skill
you wrote — a real directory in `.agents/skills/` always beats a framework skill of the same name.

## Everyday commands

```sh
node bin/sidekicks --help                      # every verb
node bin/sidekicks core status                 # framework version, mount health, upstream drift
node bin/sidekicks core update                 # move to the latest on the tracked branch
node bin/sidekicks core update --ref v1.2.3    # or pin an exact release
node bin/sidekicks core doctor                 # gate: marker, wiring, overlay, push guard, node
node bin/sidekicks project create my-app       # start working
```

`core update` **stages** the submodule change and stops. Reviewing and committing it is yours:

```sh
git commit -m "chore: update sidekicks framework core"
```

## Agent packs — shipped, never installed for you

This core carries optional **agent packs**: ready-made crews of persistent agents you can install
into your workspace. They travel inside the mount, and **nothing installs one for you** — `core
init` and `core update` create no agent, ever. You opt in:

```sh
node bin/sidekicks agent pack list              # what this core carries
node bin/sidekicks agent pack show core         # its agents, and the skills they need
node bin/sidekicks agent pack install core      # create them in YOUR .sidekicks/agents/
node bin/sidekicks agent pack status core       # ready | degraded | not-installed | invalid
```

A pack **declares** the skills its agents rely on; it never bundles or downloads one, because skills
come from the skills repository and a bundled copy would fork them. If a required skill is missing,
`install` stops **before writing anything** and prints the exact commands that fix it — typically:

```sh
git clone https://github.com/utranand/sidekicks-skills.git /tmp/sidekicks-skills
node bin/sidekicks skill import <name> --from /tmp/sidekicks-skills --with-deps
node bin/sidekicks framework sync
```

Installing is safe to repeat. An agent you already have is **never** overwritten — if the name is
already taken by an agent that did not come from the pack, that one is reported as a conflict and
left exactly as it is; if you edit an agent the pack installed, later runs leave your version alone.

## The core is read-only

`core init` arms three guards on the mount so an accidental push cannot reach this repository:

1. `origin`'s **push** url is redirected to an unreachable scheme (fetch keeps working).
2. `push.default = nothing`, so a bare `git push` refuses.
3. a `pre-push` hook in the submodule's git directory refuses every push, whatever the refspec.

**This prevents accidents, not intent.** All three are local git state, and `--no-verify` alone
defeats the hook. Enforcement that actually holds is branch protection on this repository.

## Contributing

Do not commit here — edits inside a mounted core are discarded by the next `core update`, and this
repository's contents are regenerated wholesale by `sk-inherit` from the Sidekicks source
repo. Take the change upstream, then pull it in with `core update --ref <new tag>`.

## Uninstall

```sh
git submodule deinit -f .sidekicks-core
git rm -f .sidekicks-core
rm -rf .git/modules/.sidekicks-core
```

Your `.sidekicks/`, `.agents/skills/`, `projects/` and `AGENTS.md` are yours and stay put. The
managed blocks in `.gitignore` and `AGENTS.md` are delimited — delete them by hand if you want them
gone; the import line inside the `AGENTS.md` block points into the removed mount, so it resolves to
nothing once the submodule is out.
